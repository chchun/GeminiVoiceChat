## 1. SDD 하네스란 무엇인가

코드보다 **문서(spec)가 먼저** 움직이는 개발 방식이다. AI 세션(Claude 등)이 매번
새로 시작해도 판단 기준·진행 상태·설계 근거가 파일로 남아 있어, 세션이 바뀌어도
일관된 결정을 내리게 하는 것이 목적이다.

핵심 파일 구성 (리포 루트):

```
constitution.md      ← 불변 원칙 (P1, P2, ...) — 모든 판단의 최상위
DESIGN.md            ← 현행 시스템 설계도 (지금 무엇이 어떻게 동작하는가)
specs/
  └─ NNN-기능이름/
       ├─ spec.md    ← 무엇을·왜 (범위, 계약, 수용 기준)
       ├─ plan.md    ← 어떻게 (설계 결정 D1.., 영향 파일, 리스크, 버린 대안)
       └─ tasks.md   ← 순서 (실행 태스크 + ## 기록)
CLAUDE.md            ← AI 세션 진입점 (읽기 순서·명령·함정만 — 얇게)
KICKOFF_PROMPT.md    ← 새 세션 시작 시 붙여넣는 프롬프트 원본
```

각 문서의 역할 분담이 핵심이다:

| 질문 | 답하는 문서 | 변경 빈도 |
|---|---|---|
| 절대 어기면 안 되는 것은? | `constitution.md` | 거의 없음 (개정 = 날짜+근거 spec 병기) |
| 지금 시스템은 어떻게 생겼나? | `DESIGN.md` | 구조 변경 시 |
| 이번 기능은 무엇을 만드나? | `specs/NNN/spec.md` | 기능마다 신설 |
| 어떤 설계로, 왜 그 설계인가? | `specs/NNN/plan.md` | 기능마다 신설 |
| 지금 어디까지 했나? | `specs/NNN/tasks.md` | 매 작업마다 |
| AI가 처음 봐야 할 것은? | `CLAUDE.md` | 드묾 |

### 운영 규칙 (요약)

- feature 디렉터리는 **항상 3종(spec/plan/tasks)을 모두** 갖는다. plan 없이 tasks 부터 쓰지 않는다.
- 대화로 들어온 요청도 문서에 남긴다 — 기존 spec 범위 안이면 `tasks.md`의 `## 기록`에
  한 줄, 범위 밖이면 새 `specs/NNN-*/`을 만든다.
- 원칙과 충돌하는 변경은 **constitution 개정이 코드보다 먼저**다.
- 태스크 상태 태그:
  - `[maker-ready]` — AI(maker)가 표시할 수 있는 최대 상태. **done 금지** — 완료 판정은
    fresh 세션의 checker 또는 사람 몫.
  - `[needs-device]` — 실기기/실서버 검증이 필요한 항목. 사람에게 넘긴다.
  - `[human]` — 사람만 결정/수행할 수 있는 항목 (커밋 판단, 외부 협의 등).
- 검증 결과 보고는 **자동 검증(test/빌드)과 실기기 검증을 구분**한다.
  실검증 전 "동작한다" 단정 금지.

## 3. CLAUDE.md 리팩토링 — Opus 5 / Fable 5 권장 방향

### 왜 리팩토링하는가

구세대 모델용 CLAUDE.md는 "모델이 놓칠까 봐" 모든 것을 장황하게 적는 경향이 있었다.
Opus 5 / Fable 5급 모델은 **코드를 직접 읽고 파생 가능한 사실은 스스로 알아낸다.**
따라서 CLAUDE.md에 코드에서 읽히는 내용(데이터 흐름, 함수 동작, 패키지 구조 설명)을
중복해 두면 ① 유지보수 시 코드와 어긋나 오히려 오답을 유도하고, ② 매 세션 컨텍스트를
낭비한다.

### 권장 원칙: "코드로 알 수 없는 것만 남긴다"

| CLAUDE.md에 **남길 것** | CLAUDE.md에서 **뺄 것** (→ 이동처) |
|---|---|
| 읽기 순서 (constitution → specs → design) | 상세 아키텍처 설명 → `DESIGN.md` |
| 빌드·검증 명령 + 환경 함정 (JAVA_HOME 등) | 불변 원칙 → `constitution.md` |
| 코드로 알 수 없는 함정 (삽질 이력, 기기 특성) | 데이터 흐름 단계별 서술 → 코드 자체 + `DESIGN.md` |
| 프로세스 규칙 (SDD 3종, 푸시 전 체크리스트) | 진행 상태·백로그 → `specs/`, `TODO.md` |
| 주요 코드 위치 (진입점 안내 수준) | UI 세부 구현 설명 → `DESIGN.md` 또는 삭제 |

### 이 리포의 최종 CLAUDE.md 구성 (~90줄)

```
프로젝트 개요            2줄 — 무엇을 만드는 앱인지
반드시 먼저 읽을 것       constitution → specs/NNN → DESIGN.md → 계약 문서 (순서 강제)
SDD 문서 3종             spec/plan/tasks 표 + 운영 규칙 4줄
푸시 전 체크리스트        CHANGELOG → tasks 기록 → 계약 문서 → test/build
빌드·검증 명령           PowerShell 명령 + JAVA_HOME 함정 + SDK 버전 한 줄
함정 목록                코드로 알 수 없는 것만: encodeDefaults 삽질,
                        One UI 소켓 abort, Galaxy 에러 11, WebSocket→HTTP 이행 오독 주의
주요 코드 위치           진입점 6곳 (설명은 DESIGN.md로 위임)
```

리팩토링 전에 있던 "텍스트 스트리밍 흐름 1~4단계", "보이스 플로우 상태머신",
"스마트 자동 스크롤 동작" 같은 절은 전부 `DESIGN.md`로 옮겼다 — 이것들은 설계
문서이지 세션 진입 지침이 아니다.

## 4. DESIGN.md 구성 방법

DESIGN.md는 **"현재 구현된 시스템"의 단일 설계도**다. 미래 계획(→ spec)도,
이력(→ app/docs, CHANGELOG)도 아니다. 이 리포의 목차:

| 절 | 내용 | 작성 요령 |
|---|---|---|
| §1 제품 정의 | AI 챗봇, 입력(텍스트+음성)·출력(마크다운+A2UI 서피스) | 3~5줄. "이 앱이 뭔가"에 즉답 |
| §2 계층 구조 | 패키지 트리 + 의존 방향 | ASCII 다이어그램 하나 |
| §3 응답 스트리밍 파이프라인 | 입력→POST→SSE/NDJSON 파싱→이벤트→상태→렌더링 | **가장 중요한 흐름 하나를 끝까지** 추적 |
| §4 A2UI 생성형 UI | 서피스 구조, 컴포넌트 14종, 바인딩, 상호작용 | 상세 계약은 08 문서로 위임, 여기는 지도 |
| §5 보이스 설계 | 상태머신 + Samsung 하드닝 요약 | |
| §6 UI 세부 결정 | 자동 스크롤, 키보드 dismiss | "왜 이렇게 했나"가 남을 결정만 |
| §7 빌드 구성 | local.properties 플래그 표 | |
| §8 문서 지도 | app/docs 각 파일의 역할 + **구식 문서 경고** | 오독 방지가 목적 |

작성 원칙:
- **구식 정보를 발견하면 지우지 말고 표시한다** — 이 리포는 WebSocket → HTTP POST로
  이행했는데 `03_server_api.md`가 WebSocket 기준이다. DESIGN.md §8에 "⚠ 이력이다,
  현행은 여기"라고 명시해 새 세션의 오독을 막았다 (개정 작업 자체는 spec 태스크로).
- 코드와 1:1로 중복 서술하지 않는다. 흐름(무엇이 무엇을 거쳐 어디로)과
  결정 근거(왜 sealed class인가)만 남긴다.

## 6. 자주 하는 실수

- **tasks.md만 만들고 plan을 건너뛰기** — "왜 이 설계인가"가 없으면 다음 세션이
  같은 대안을 다시 검토한다. plan의 "버린 대안" 표가 하네스의 절반이다.
- **CLAUDE.md에 설계를 다시 쌓기** — 리팩토링 후에도 편하다는 이유로 CLAUDE.md에
  흐름 설명을 추가하면 원점 회귀. 설계는 DESIGN.md로.
- **AI가 done을 찍게 두기** — 완료 판정은 사람/checker 몫. `[maker-ready]`에서 멈추는지 확인.
- **constitution을 자주 고치기** — 자주 바뀌면 원칙이 아니다. spec 수준 규칙은 spec에.
- **소급 기록 생략** — 이미 짠 코드라도 spec 없이 두면 다음 세션이 의도를 추측한다.
  이번 specs/001처럼 소급으로라도 3종을 만든다.
